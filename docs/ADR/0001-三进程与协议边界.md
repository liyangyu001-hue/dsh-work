# ADR-0001 · 三进程与协议边界

- 状态：已采纳
- 日期：2026-10-19

## 背景

需求里有三条硬约束同时存在：

1. 顶栏必须**系统级置顶、跨应用可见**；
2. 热键要能在**任何应用**里唤起；
3. 要能**截取屏幕**来理解人在做什么。

而 DSH 的两端各自封着门：客户端 bundle 只拿得到平台基线（React 等），`require('electron')` 直接抛错；插件宿主是 `ELECTRON_RUN_AS_NODE` 起的纯 Node 子进程，`globalShortcut` / `desktopCapturer` / `Tray` 物理上不存在。DSH 主窗口的权限处理器只放行单轨音频，`getDisplayMedia()` 必被拒。

## 选项

- **A. 全塞进插件**：做不了 1/2/3，直接排除。
- **B. 插件 + 自绘窗口（用 DSH 窗口冒充顶栏）**：不是系统级置顶，跨应用就消失，排除。
- **C. 加一个真正的外部进程**：能做成，代价是多一个进程要管。

## 结论

选 **C**，并把边界钉死：

- **Host（插件）是唯一真相源**，持有状态机与持久化；
- **Companion 不持有业务状态**，只做感官（截图、热键）与脸（顶栏、托盘）；
- 两者只通过 `docs/PROTOCOL.md` 的报文通信，Companion 崩溃重启后从 `snapshot` 恢复。

## 后果

- 好处：伴随层可被整体替换（换 Rust/Tauri/原生 .NET 都不动业务代码）；Host 可单测；崩溃可恢复。
- 代价：多一个进程的生命周期管理，需要处理「Host 没起来时 Companion 显示什么」。
- 约束：**任何在 Companion 里缓存业务状态并据此做判断的代码，都是对这条 ADR 的违反**。
